## 1. Root cause (single forensic finding for both P0s)

`ACTION → HANDLER → DOMAIN → DB → AUTHORITATIVE STATE → AGGREGATION → VIEW`

The **first broken layer is DOMAIN LOGIC / AGGREGATION**, and it is the *same*
break for both KPIs:

- A reservation is created with `status = "RESERVED"` (desktop `_create_reservation_record`,
  backend `_process_reservation_create`, `RentalService.create_rental`).
- **No client — desktop or mobile — ever moves a reservation to `ACTIVE`.**
  `POST /rentals/{id}/activate` exists, `ApiClient.activate_rental()` exists,
  but **no UI ever rendered an "Activer" control**. Reservations only ever go
  `RESERVED → COMPLETED` (or `CANCELLED`).
- The old canonical rule was **status-derived**:
  - `RENTED` bucket = vehicle with an **`ACTIVE`** reservation covering now.
  - `Revenue` = `SUM(total_price) WHERE status IN ('ACTIVE','COMPLETED')`.
- Therefore every real booking sat in `RESERVED` forever and contributed **0**
  to "Véhicules en location" and **0** to "Chiffre d'affaires". The KPIs were
  not lying about their inputs — the rule itself could never see a real rental.

Persistence was fine: `total_price` **is** computed (`daily_price * num_days`,
rounded) and **is** persisted (`Reservation.total_price`, `Numeric(12,2)`), on
all three write paths. No null, no string/number bug, no cents/MAD mismatch,
no wrong column, no timezone bug in the period math. The number was correctly
**0** for the rule as written.

## 2. Final canonical rule (user decision 2026-09-01: "time-derived")

Normative spec: `shared/fleet_status_reference.py`.
Parity vectors: `shared/fleet_status_cases.json` (14 cases), regenerated by
`scripts/regen_fleet_status_cases.py`, enforced against **all three runtimes**
by `test_fleet_status_crossruntime.py` (backend), `test_fleet_status_crossruntime.py`
(desktop), `FleetStatusParityTest` (mobile).

### 2a. "Currently in location" / RENTED bucket

For a reservation interval `[start, end)` whose status is **RESERVED or ACTIVE**
(a *blocking* reservation) and is **not CANCELLED**:

| condition            | effective bucket |
|----------------------|------------------|
| `start <= now < end` | **RENTED** ("en location") — the car is physically out |
| `now < start`        | **RESERVED** (upcoming booking, surfaced for staff) |
| `now >= end`         | free (AVAILABLE unless another interval applies) |
| status `CANCELLED`   | never counts |

Precedence (mutually exclusive): `SOLD/INACTIVE > MAINTENANCE > RENTED > RESERVED > AVAILABLE`.
`RENTED` is **time-derived, not status-derived**: this business hands the car
over at the reservation start and has no separate "pickup" step, so a
`RESERVED`-status reservation whose window contains `now` is `RENTED` exactly
like an `ACTIVE` one.

### 2b. Revenue

```
Revenue(period) = SUM(total_price)
                  WHERE status != 'CANCELLED'
                    AND start_datetime <= now              (rental has started)
                    AND period_start <= start_datetime < period_end
```
Period bounds in `Africa/Casablanca` local time; week starts Monday; month =
calendar month. Revenue is **recognised when the rental starts**. A cancelled
rental never counts. A not-yet-started future booking contributes **0** to
current revenue but is still counted under the "réservations" *count* cards.

The same eligibility rule (`!= CANCELLED`, started) was applied to the
previously-inconsistent siblings: `today_returns`, per-vehicle performance
stats (`get_vehicle_stats`), and the client report's `active_rentals` ("En
cours") KPI — see §9.

## 3. "Activer" implementation and semantics

- Desktop `ReservationWidget`: a blue **"Activer"** button is rendered **only**
  on rows whose status is `RESERVED` (i18n key `reservations.action_activate`,
  fr `"Activer"` / ar `"تفعيل"`), alongside the existing Terminer / Annuler.
- `_activate_reservation(rid)` → `_set_reservation_status(rid, "ACTIVE")` — the
  **same** canonical write path as Complete/Cancel: one `DomainStore.mutate()`
  transaction, one published store revision, one `("reservation","UPDATE")`
  sync-queue item (`{"id": rid, "status": "ACTIVE"}`), applied server-side by
  the existing `_process_reservation_update`.
- **Operational status and physical rental window are kept strictly separate.**
  Activer changes the operational status only. It is **not** a precondition for
  any KPI and **does not change** them: a `RESERVED`-covering-now reservation is
  already `RENTED` / revenue-eligible. Proof:
  `desktop/tests/test_activer_action.py::test_activer_transitions_status_but_kpi_stays_rented`
  — `rented == 1` before the click, `status == "ACTIVE"` after, `rented == 1`
  still after.

## 4. Client write-back implementation and proof

Desktop `ReservationFormDialog` (New Reservation form):

- **Stale-data fix** — `_on_client_selected`:
  - selecting an existing client now also loads `cin_number` (added to the
    selector projection);
  - selecting **"Nouveau client"** (or index 0) now **clears** name / phone /
    email / CIN and the four document paths — no identity leak between
    reservations;
  - a snapshot `_loaded_client_fields` is taken so edits can be detected.
- **Write-back** — on save, if an existing client is selected **and** any of
  name/phone/email/CIN differs from the loaded snapshot, `_create_reservation_record`
  updates the linked `LocalClient` row (`first/last_name`, `phone`, `email`,
  `cin_number`, `updated_at`, `version += 1`) **and** enqueues a
  `("client","UPDATE")` sync item — **inside the same transaction** as the
  reservation create (atomic: a failure rolls back both). The reservation keeps
  `customer_id`. No write-back when nothing was edited; an existing client is
  never re-`CREATE`d.
- Backend `_process_client_update` already persists exactly these fields.

Proof — `desktop/tests/test_client_workflow_forensic.py` (5 tests):
`switching_between_clients_no_stale_data`,
`new_client_after_existing_selection_clears_fields`,
`editing_existing_client_writes_back_to_client_record`,
`unedited_existing_client_saves_with_no_writeback`,
`reopen_shows_persisted_updated_data_not_stale`.

## 8. Numerator / denominator of "Véhicules en location"

- **Numerator** = count of non-`SOLD`/`INACTIVE` vehicles whose effective
  status is `RENTED` = has a blocking reservation (`RESERVED` or `ACTIVE`,
  not `CANCELLED`) with `start <= now < end`, and no active maintenance
  covering now (maintenance wins).
- **Denominator** = `total_vehicles` = count of vehicles that are neither
  `SOLD` nor `INACTIVE` (the four operational buckets sum to it exactly).
