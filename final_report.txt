A. ROOT CAUSE
The bug consisted of a severe UI flow defect combined with a transaction boundary violation. When creating a reservation with a new client, the form dialog always closed unconditionally even if the reservation was rejected by the backend or local overlap check.

B. CODE PATH
`ReservationFormDialog._on_save()` emitted the `saved` signal and then immediately called `self.accept()`. The slot `ReservationWidget._create_reservation_record()` executed synchronously, and if it encountered a blocking reservation (e.g. from a prior test run on the server), it displayed the "double booking" warning and returned. Control flowed back to `_on_save`, which executed `self.accept()` and destroyed the dialog, losing all client input.

C. WHY CLIENT FORM TRIGGERED IT
When filling out a "Nouveau client", the user enters significant data. If a real backend conflict exists (such as a forgotten test reservation on the server), the backend correctly blocks it. But because the dialog closed instantly after the error, the user assumed the error was a "false positive" bug triggered by the new client creation, rather than a genuine conflict that simply wasn't handled gracefully in the UI.

D. EXACT FIX
1. Added `_creation_succeeded` flag to `ReservationFormDialog`.
2. Modified `ReservationWidget._open_new_reservation_dialog` to track the active dialog.
3. Modified `ReservationWidget._create_reservation_record` to set `_creation_succeeded = True` only on success.
4. Wrapped `self.accept()` in `_on_save()` to only execute if `self._creation_succeeded` is true.
5. Removed the internal `self._session.commit()` from `SyncQueue.enqueue()` in `desktop/app/sync/queue.py` to restore transaction atomicity.

E. DB INTEGRITY
PostgreSQL was not touched. Local SQLite was not reset by the fix (only by test environment variables). Data sync overlap protection is preserved.
